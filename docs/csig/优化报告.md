## 1. 交付结论与实验口径

**单卡 BF16、MTP 关闭，恰好三个优化点：MoE 专家计算、Attention 计算、分段编译与 Graph 执行。** 当前完整验收版本为 `73d21d03`。公开集三轮测试中，A 吞吐中位数 **697.738 token/s/GPU，比题目基线高 9.31%**；B 单流 TPOT p50 为 **9.205 ms**；C 的两项 p99 仍高于基线。没有把未达标的 C 写成性能通过，也没有把公开集测试写成隐藏集验收。[E1–E3]

| 指标 | baseline.json | 三轮完整实测 | 三轮中位数与判断 |
|---|---|---|---|
| A tok/s/GPU ↑ | 638.2827 | 670.5907 / 697.9714 / 697.7380 | 697.7380；提升 9.31% |

**基线来源。** `/data/datasets/baseline.json` 明确记录单卡、eager、compile level 0、BF16 KV、MTP off、SWA on。638.28 是其中 A 的输出吞吐，不是 B 单流速度，也不是本次另跑 HF 得到的数值。附近的 `humaneval_bf16.json` 为 3/164，但 baseline 已将其标记为聊天模板/思考模式不一致的无效协议，不能作精度对照。[E1]

**负载与计时。** 冻结容器内一张 MI308X，PCI `0000:22:00.0`；A512、并发32；B50、并发1、输入1024；C200、开放环泊松率0.30请求/秒、总超时180秒。均流式输出256 token、greedy、忽略 EOS，随机种子20261105。每场景独立计算分位数，再对三轮指标取中位数，不合并请求求一个 p99。三轮主测试共2286个请求，全部成功且均输出256 token；源码、依赖快照不变，正式计时不启用 profiler。[E2]

**数据适配边界。** EvalScope 1.14.1 不接受文件路径作为 dataset 插件名，A 通过 `line_by_line` 原样读取 prompt。主结果保留原文件512条，其中5条实际长度4097–4113；额外筛出507条合规提示并循环至512条的补充结果为704.589 token/s/GPU，不替换主结果。测试在同进程正确性检查及预热之后执行，持久编译缓存已存在；不将该结果称为冷启动性能。

## 3. Profiling 证据与三个优化点的选择

选择顺序遵循“正确性兼容路径 → 工具时间线 → 单点替换 → 完整模型验证”。参考路径中逐请求 GEMM、显式 Attention、专家循环适合定位误差，却保留大量 launch、权重搬运和无效窗口外计算。三个优化点分别对应专家计算、Attention、执行提交，边界由独立开关控制，Norm/Linear/RoPE 的基础精度适配属于共同 Step 0，不额外包装成第四个点。

**已有工具证据。** 历史中间版本 A32 prefill 的 torch profiler 原始 trace 共32159个 GPU kernel 事件，累计9.216秒；MoE 3.205秒（34.8%）、GEMM 2.990秒（32.4%）、其他3.022秒（32.8%）。分类按 kernel 名称，GEMM 同时包含投影和 Attention；累计 kernel 时间不是请求墙钟时间，有并发时不能直接相加解释延迟。这支持优先检查 MoE 和矩阵计算，但不是最终版本的耗时占比。[E5]

**当前版本工具输出。** `delivery_profile_20261105T183352Z` 保留同一启动环境，预热后分别采集：短输入单流输出64 token（36395事件、累计464.48ms）；16k输入输出8 token（5699事件、2102.18ms）；A32各输出8 token（35236事件、10146.41ms）。16k窗口中，GEMM672.31ms、softmax556.38ms、MoE469.07ms，分别占32.0%、26.5%、22.3%；说明长请求仍有明显矩阵计算和归一化成本。窗口包含少量decode，不能称为纯prefill时间，也不能把诊断墙钟当作无profiler性能。[E5]

### 点 1：MoE 专家计算

64专家、top-8、hidden2304、专家中间维896。以原生 CK 两阶段专家核恢复批量计算，复用路由与缓冲，使用 BF16 路由融合、独立 slot 输出和有序归并，减少重复路由、碎片 GEMM 及搬运；按已验证形状选择 stage1/stage2 的计算参数。两条 prefill stream 仍属于同一专家计算实现。

**原核为什么不能直接用。** 融合 kernel 的中间 BF16 舍入位置、K 维累加顺序、top-k 加权和输出累加次序不同，固定输入的微小差异会改变后续 greedy 分支。修复采用同输入中间张量定位并保留有序输出；不以权重相同或局部误差小代替整模型验收。主要入口为 `mellum_native_decode_moe.py`、`mellum_native_prefill_moe.py` 及打包 AITER/CK 修改源，文件和依赖哈希见代码索引。[E4]

### 点 2：Attention 计算

21层采用1024滑窗、7层全注意力。decode 使用修正的 AITER/Gluon 路径；prefill 对滑窗只计算有效 QK、softmax 与 PV 区域，并保留 HF 的 BF16 舍入和归约顺序。QK/PV 参数来自冻结 hipBLASLt 对1–16384长度的形状查询，不按提示内容、题号或答案选择实现；未知形状、布局或 dtype 回退到正确性兼容路径。

**逐核反例与修复。** QK 统一使用 KW8 在长度7169出现8177个 BF16 不同值，改为 MI、depth、row-tile 分派；PV 主循环采用 KW8，最后不足一个块的尾部采用 KW4，修复长度4095下4个尾行差异；窗口 softmax 缓存1024有效元素，保持 ATen 512-lane归约次序和行对齐。窗口外概率不写入，但与之成对的 PV 对每次读取施加掩码，不能交给无掩码的 dense fallback。[E6]

**固定形状收益。** 16k窗口 PV 12.19→2.65 ms，窗口 softmax 30.28→5.84 ms。QK/PV/softmax 均保留边界长度与40次重复检查；固定输入通过之后再执行整模型门槛。这些微基准不等于 C p99 改善比例。当前全量 C 相比上一完整版本的124.77/10512.69 ms降至68.33/4387.40 ms，但仍未达到题目基线。[E2、E6]

<!-- pagebreak -->

### 点 3：分段编译与 Graph 执行

对稳定的小计算段启用 `ATOM_MELLUM_COMPILE_PIECES=1`，使用 ATOM decode graph，捕获批次1/2/4/8/16/32；把动态请求元数据与可重放计算分开，维持稳定地址、偏移和缓存生命周期，降低每 token 的 Python 提交和小算子启动成本。`ATOM_MELLUM_GRAPH_PIECES=0`，未叠加另一套分段 graph；服务命令的 `--level 0` 与显式的小段编译是两个层次。关闭点3时强制 eager，并关闭分段编译。

图执行也必须验证输出，不能假设“不改算术就没有精度风险”。稳定元数据与数值形状约束在 eager 对照中也保留，点3消融比较的是编译与重放。冷捕获、首次编译、稳定重放分别记录；性能测试排除 profiler。控制参数和展开环境写入启动 manifest，避免只根据命令判断实际路径。[E4]

## 5. 取舍、已知限制与后续方向

**MTP未采用。** 曾有短输入单流小测收益，但长上下文、混批、缓存与图捕获组合需要独立完整验收；投机接受率不能替代目标模型输出一致性。遵照最终范围，MTP 默认关闭，不作为三个优化点之一。**量化未采用：** 需重新满足精度门槛，当前 BF16 误差已经对 greedy 决策敏感。**双卡 TP/PD 未采用：** 额外通信和按卡数归一化收益缺少完整实测，且双卡输出需重新验证；本次只交单卡。

**前缀缓存与 chunked prefill 未纳入。** 前者保持题目 Step 0 关闭设置；后者改变 GEMM 的 M 维及专家分组，不能只凭理论判断其精度和 C 收益。**未盲目恢复所有原始 fused kernel：** 通用融合改变舍入/归约次序的反例已保留，当前只启用已验收的 native 参数路径，未知形状仍回退。C 剩余差距应继续从长 prefill 和 decode 的时间线定位，不能靠更改请求、降低输出长度或选择最好一轮掩盖。

## 6. 代码仓库、开关与复现

在题目冻结 Linux 容器、模型已位于 `/data/models/Mellum2.1-12B-A2.5B-Thinking` 的条件下，仓库根目录执行：

```bash
bash scripts/start_server.sh
/opt/venv/bin/python3 scripts/validate_public.py
bash scripts/benchmark.sh --repeat 3
```

启动脚本校验源码和依赖 SHA256，自动解包本仓库运行依赖，加载、预热并完成一次真实8-token生成后才打印 READY。默认8000端口、三个点全开、MTP off；可指定 `--gpu`、`--port`、`--host`。本次实测 HIP设备1、ROCR设备0,1，但只使用一张物理卡。不会停止其他仓库或其他用户的服务。[E4]

| 点 | 独立开关 | 累加配置 |
|---|---|---|
| 1：MoE | `--moe-opt 0/1` 或 `OPT_MOE=0/1` | `--ablation point1` |
| 2：Attention | `--attention-opt 0/1` 或 `OPT_ATTENTION=0/1` | `--ablation point12` |
| 3：编译与图 | `--compile-graph-opt 0/1` 或 `OPT_COMPILE_GRAPH=0/1` | `--ablation point123`（默认） |

`--ablation step0` 关闭三个点；切换前用 `python3 scripts/stop_server.py --port 8000` 正常停止本仓库服务。`--screen` 仅用于小测。源码和原生 AITER/CK 修改、生成实例、构建记录、二进制哈希均随仓库保存；默认使用冻结环境中已验证的二进制，**未声称已在全新环境从源码重建通过**。完整 Git 历史保留，不 squash；AI说明与 D1–D7 日志单独交付。
