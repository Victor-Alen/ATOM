# 10 分钟问答准备

主讲结束后按问题回答，不连续朗读全部备答。优先准备前六题，每题约 60–90 秒；其余用于追问。最终数值以报告和 PPT 的全量结果页为准。

## 1. 为什么正确性花了这么久？最关键的发现是什么？

最关键的发现是，矩阵输入的一行相同，并不意味着批次变化后这行 BF16 输出一定相同。底层库会按矩阵形状选择不同的 MFMA 和归约顺序，而后续 greedy 解码会放大临界位置的差异。早期逐请求 Norm、GEMM 和显式 attention 是定位工具，确实带来了很大的性能代价。后来我把问题拆到 BF16 舍入点、K 累加次序和输出归并顺序，再逐个恢复原生并行路径。固定输入逐位相等只是第一层证据，最终仍要走自由生成、16k 和 HumanEval。

追问时可举两个具体反例：长 QK 统一使用 KW8 在 7169 长度失败；PV 主 K 块正确后，4095 长度的尾 K 块仍有 4 个 BF16 值不一致，最后通过尾块 KW4 修正。试错记录保留在 `research/operator-validation/`。

## 2. 你真的超过了 baseline 吗？638.28 是怎么来的？

638.282724 是机器上 `/data/datasets/baseline.json` 给出的 A 场景每卡输出吞吐，它是出题方朴素移植的基线，不是我另跑的 HF 吞吐。C 要比较同一文件中的 TPOT p99 41.265 ms 和 TTFT p99 993.549 ms。B 没有给基线，因此只能报告绝对值。

附近的 `humaneval_bf16.json` 记录过 3/164，但 baseline 已明确标为 rejected：当时未按聊天模板和 thinking 协议生成。不能拿这个废弃值宣称精度巨大提升；报告采用另行冻结、同协议 HF 对照的 148/164。

我会逐指标回答：A的完整公开集结果超过了该吞吐基线；C两项p99仍未达到，不能用吞吐或小样本p99替代。即使某个算子快了五倍，也不等于所有端到端场景都达标。同机另一张卡存在独立服务，本次不称为整机空闲测量；隐藏集及正式空闲环境由裁判复测。

## 3. 三个点怎么划分？是不是把很多优化打包成一个点？

三个点分别对应三个可辨识的瓶颈，并有各自开关。第一点是MoE专家计算，范围是路由、两阶段专家GEMM和按slot有序归并；第二点是Attention的QK、softmax、PV计算，滑窗省去窗口外区域，全局QK跳过未来块，softmax复用保序归约数据；第三点是片段编译与解码图执行，减少重复的主机提交。

Norm、Linear、RoPE 的数值适配放在共同的 Step 0 基础里，不再冒充额外优化点。累计消融依次开启三个点，同样的精度小门槛在每一行重新检查。各个候选的独立开关仍保留，便于追到具体实现。

## 4. 为什么不用 MTP、双卡或量化？

MTP 确实做过研究和对照，也观察过短提示收益，但最终按约定关闭。开启它需要独立证明 on/off 逐 token 一致，并检查完整负载、长上下文与缓存容量；不能只用短提示的接受率决定交付。当前三点预算用在已经逐项核查的计算和执行路径上。

双卡会增加系统形态和通信复杂度，A 还必须按卡数归一化；只看总吞吐翻倍没有意义。量化也需要重新通过精度门槛。最终声明只使用一张卡，不声称未经验证的双卡或量化收益。研究分支和失败记录保留，但不混入默认启动配置。

## 5. C 的尾时延为什么难？下一步会怎么做？

C 的请求是泊松到达，包含 4k–16k 的长输入。长 prefill 与进行中的 decode 竞争同一张 GPU，因此请求等待、长算子和调度会共同影响 p99。缩短 SWA 的 QK、softmax、PV 已经减少了这部分工作，但七层全注意力、MoE、其他计算和排队仍然存在。

下一步应该用最终版本的时间线判断剩余占比，再在三点预算内优先减少注意力中的无效工作。调度、chunked prefill 或前缀缓存可以作为后续方向，但它们改变形状或执行条件，需要新的正确性和完整 C 测试；我不会把尚未通过的方案写进这次默认版本。

## 6. AI 做了多少？你如何知道它说的是对的？

用了 Codex 和词元工坊辅助阅读代码、写探针、改算子、整理日志。AI 能快速提出方案，但也曾把局部对齐解释成整体问题解决，或者在 MTP 的结构假设上出错。我通过重新读模型配置、检查真实调用路径、固定输入反例以及完整自由生成来纠正。

这次最需要改进的是我自己的目标管理：始终知道 baseline、当前运行版本和未解决问题，不能把连续追问当成理解了代码。AI 使用说明保留这些错误和我的决策，工作日志也不倒填成一周内全部完成。

## 其他常见追问

**为什么不是直接 FlashAttention？** 已分别只恢复原生融合prefill的全部层、全注意力层、滑窗层，C200一致率为46.37%、55.30%、45.41%，均没有达到90%门槛。三个实验的16K单样例都一致，也不能据此放行。融合改变softmax、QK/PV的中间BF16边界和累加顺序，当前保留分拆的QK/softmax/PV；不能宣称所有原始融合核都已恢复。

**HF参考到底是哪一种？** C200明确对照冻结的HF eager输出，文件哈希固定。历史目录另有SDPA输出，但原始配置是否完全相同未在本次审计中建立，不能把两者直接替换，或把差异只归因于Attention后端。交付材料分别标明性能baseline、正确性参考与隐藏集未验收的边界。

**C有共享前缀，为什么还关闭prefix cache？** 题目允许把前缀缓存作为优化方向，并非禁止开启。当前三个点选择了专家计算、Attention计算、编译与图执行；前缀复用会改变实际prefill范围和矩阵形状，还需独立证明数值与完整C收益。交付保留关闭设置，没有把未经完整验收的缓存收益并入已有三个点。这个取舍限制了C的提升，也是本次时间分配需要复盘的地方。

**形状表是否针对公开集作弊？** 表来自冻结hipBLASLt对完整长度区间的算法查询，依据长度、dtype、布局与设备架构分派，不依据prompt文本、数据集ID或参考答案；未知条件回退到兼容计算。运行时不加载 `validation/references/`。完整区间的算法查询不等于穷举了每个长度的端到端精度；实际验证范围以边界形状探针、公开集和明确列出的16K检查为准。

**窗口外内存未初始化是否安全？** 仅在成对的稀疏 softmax/PV 路径使用；每次加载都以 causal/SWA 条件屏蔽窗外位置，结果不暴露给 dense PV。shape 或布局不匹配时先回退，不能把部分写入的张量交给不具备掩码的消费者。

**微基准的加速为什么不能直接加起来？** 核函数时间、GPU 并行时间和 HTTP 请求时间的分母不同；kernel 在多个 stream 上还可能重叠。最终通过同条件累计消融和完整场景测量判断，不能相乘独立倍率。

**消融为什么用小样本？** 为高效筛选，每行统一使用 A64/B8/C12 一轮，表上明确写出样本量；C 的 p99 只是小样本估计。最终候选另外执行 A512/B50/C200 三轮，未把消融表冒充完整验收。

**三轮取中位数怎么计算？** 每轮先由 EvalScope 得到该场景指标，再对三轮同一指标取中位数；不是先合并全部请求重算分位数。每轮请求数、成功数和输出长度都有原始记录。

**最终候选是否每个指标都最快？** 不是。最后两版完整对比中，9c52的A/B中位数略好，0453的C两项p99略低。最终按提前登记的规则优先降低C TTFT，同时要求A、B及C TPOT不退化超过1%，所以选择0453。差异都不到1%，没有统计显著性结论；各项最佳值另列在《最终候选对比》，不会拼成一个不存在的配置。

**C为什么每轮要十多分钟，命令里不是180秒吗？** 当前冻结客户端把 `--total-timeout 180` 传给HTTP单请求的总超时，并非把整个200请求测试截断在180秒。0.30请求/秒下，200次泊松到达本来就约需十多分钟；全部200条发出并完成后才统计。代码依据为EvalScope的 `perf/core/http_client.py` 中 `aiohttp.ClientTimeout(total=...)`。

**为什么 A 数据集做了读取适配？** 冻结客户端不支持把文件路径直接当作 dataset 插件名，因而采用 `line_by_line` 并原样传递 prompt。默认完整保留 512 条，其中 5 条实际 tokenizer 长度略大于 4096；过滤版仅作单独补充，不替换主结果。

**Graph 是否等于开启 level 3？** 默认服务仍用 level 0 包装数值兼容路径，内部显式编译稳定的 tensor pieces，并使用 ATOM decode graph。报告说明实际开关，不把配置等级名当成已发生的编译证据。

**关闭点3是否也关闭元数据缓存？** 不会。稳定元数据与数值形状约束是所有行共享的基础，点3开关比较小段编译与graph重放，并在关闭时强制eager。不能把共同基础的收益再次归到点3；本项目Step 0也不等于出题方baseline。

**是否从源码完整重建验证过？** 修改后的 AITER/CK 源码、生成实例、构建记录和原生二进制已打包，实际运行验证使用这份冻结二进制。没有声称在任意全新系统上完成了从零重建；运行前提是题目给定环境。

**HumanEval 148/164 是否足够？** 题目要求 BF16 与 HF 的 pass@1 差距不超过 2 个百分点。本协议双方均为 148/164，差距为 0；同时当前冻结验收的 164 条完整输出序列也与 HF 相同。这个结论绑定生成模板和长度设置，不外推到其他协议。

**为什么日志超过 D1–D7？** D1–D7 按实际日历和历史提交整理，11 月 4 日以后单列补充。早期 Step 0 卡得较久，这正是时间分配上的教训；保留真实日期和完整历史比制造符合预期的七天故事更重要。

**如何现场复现？** 在冻结容器中检出提交，运行 `bash scripts/start_server.sh`；真实生成成功后运行 `scripts/validate_public.py` 和 `bash scripts/benchmark.sh --repeat 3`。开关、环境摘要与日志路径见仓库 `README-CSIG.md`，停止服务使用只识别本次进程的 `scripts/stop_server.py`。
