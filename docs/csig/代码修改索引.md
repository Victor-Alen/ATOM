## 三个优化点的实现

| 点 | 主要入口 | 关键修改 |
|---|---|---|
| 1：MoE 专家计算 | `atom/model_ops/moe.py`、`mellum_native_decode_moe.py`、`mellum_native_prefill_moe.py` | 恢复原生 CK 两阶段专家计算；保留 HF 的 BF16 舍入边界与有序归并；避免原子累加顺序变化 |
| 1：路由和分组 | `mellum_native_prefill_hybrid_core.py`、`mellum_native_prefill_hybrid_routes.py`、`mellum_native_prefill_rotv1m32.py`、`mellum_native_prefill_rotv1m32_routes.py`、`mellum_native_prefill_down.py`、`mellum_prefill_streams.py` | GPU 路由计划、按形状选择累加顺序、路由复用、独立 slot 输出及 prefill stream；这些属于同一个 MoE 优化点 |
| 2：Attention 接入 | `atom/model_ops/attention_mha.py`、`mellum_bf16_attention.py`、`mellum_paged_decode.py`、`mellum_batch_decode_attention.py` | 使用通过验证的 AITER/Gluon decode 实现；prefill 保留 BF16 中间边界并按条件分派 |
| 2：窗口计算 | `mellum_prefill_sparse_qk.py`、`mellum_prefill_sparse_pv.py`、`mellum_prefill_softmax_window_sparse.py` | 只计算并读取滑窗内有效区域；QK/PV 的 MFMA 与尾块累加顺序按冻结 HF 形状查询匹配 |
| 2：softmax | `mellum_prefill_softmax_hybrid.py`、`mellum_prefill_softmax_gluon.py`、`mellum_prefill_softmax_runtime.py`、`mellum_prefill_softmax_adaptive.py`、`mellum_prefill_softmax_large_cache.py`、`mellum_prefill_softmax_window_cache.py` | 组合 scale/mask/softmax，保留 ATen 归约树、行对齐与指数下溢处理；按形状选择缓存策略 |
| 2：形状查询 | `scripts/query_hf_qk_profiles.cpp`、`scripts/query_hf_pv_profiles.cpp` | 查询冻结 hipBLASLt 的 1–16384 长度计算参数；依据张量形状，不能依据提示内容或答案分派 |
| 3：编译与图 | `atom/model_ops/mellum_piecewise.py`、`mellum_request_gemm.py`、`atom/model_engine/model_runner.py`、`llm_engine.py` | 小计算段编译、稳定请求元数据、缓存生命周期、ATOM decode graph；关闭点3时强制 eager |

`mellum_*.py` 简写均位于 `atom/model_ops/`。报告只计以上三个点。

## Step 0 的共同精度适配

`layernorm.py`、`mellum_native_norm.py`、`mellum_hf_norm.py`、`mellum_decode_norm.py` 修正残差与归一化的舍入/归约边界；`linear.py`、`mellum_native_linear.py`、`mellum_request_gemm.py` 保留必要的参考 GEMM 形状；`mellum_hf_rope.py` 处理 RoPE 计算顺序。这些适配是所有消融行共有的基础，不重复计作优化点。不能由“原生 Norm 已接入”推断所有形状都已消除兼容路径。

`atom/entrypoints/openai/protocol.py` 与 `serving_completion.py` 增加可选 token IDs 返回，供精确比较；`sampler.py`、`embed_head.py` 有精度/形状相关适配。服务端不会导入 `validation/references/` 中的 HF 答案。

## AITER / CK 的真实源码修改在哪里

启动后解包目录为 `.runtime/<归档摘要>/`。其中 `sources/` 保留原始算子库源码，`runtime/` 保留生成的 HIP/CK 实例与原生二进制，`build-history/` 保留构建脚本。每个文件的原来源、大小、SHA256 见 `deployment/runtime-manifest.json`。

重点审查：

- AITER 的 `csrc/kernels/rmsnorm_quant_kernels.cu`、`csrc/include/rocm_ops.hpp`、`aiter/ops/rmsnorm.py`：BF16 RNE、残差/中间值舍入、请求分组。
- AITER 的 `aiter/ops/triton/gluon/pa_decode_gluon.py`：HF 顺序下的 QK、softmax、PV 与分页 decode；末次工作区改动另存于 `deployment/aiter.working-tree.patch`。
- CK 的 `include/ck/tensor_operation/gpu/grid/gridwise_moe_gemm.hpp`：专家输出的 BF16 边界、路由权重舍入、独立 slot 写回。
- CK 的 `include/ck/tensor_operation/gpu/block/blockwise_gemm_pipeline_xdlops_b_preshuffle_gufusion_v3.hpp`：累加/分组与 MFMA 路径适配。

`deployment/history/` 保存四条外部算子分支的增量 bundle、逐提交 patch-series、commits.tsv 和基点索引。外部 bundle 是相对于公开上游基点的增量，恢复前须具备对应基点；ATOM 主仓库本身保留完整历史。patch-series 可能包含继承的上游提交，不应把其中每一行都认作本项目独立贡献。完整最终源码快照与 manifest 才是实际部署依据。
