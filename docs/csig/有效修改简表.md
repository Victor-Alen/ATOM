# 从模型接入到当前版本：有效修改简表

按功能归并，同一处反复调参合并成一条。依据当前交付源码、默认 fast 配置和验收记录整理；主线默认关闭 MTP，MTP 部分对应独立验证分支。

| 序号 | 修改 | 瓶颈或问题 → 具体改法 |
|---|---|---|
| 1 | 模型注册与权重加载 | ATOM 原先不认识 Mellum，也不能直接按它的结构加载权重。补齐模型注册、配置解析和专家权重映射，先让模型正确跑起来。 |
| 2 | 混合注意力与滑窗边界 | 不同层使用不同注意力范围，窗口边界处理不对会漏看或多看历史。按层配置区分滑窗和全注意力，并修正生成时的可见范围。 |
| 3 | RoPE / YaRN | 位置编码的频率、缩放和计算顺序与参考实现有差异。按层读取对应参数，匹配参考计算，并缓存可复用的位置编码。 |
| 4 | 贪心采样 | 原采样分支可能在本应确定选择的场景走到带随机噪声的逻辑。为 greedy 显式使用 argmax，排除采样本身引入的变化。 |
| 5 | RMSNorm 与残差 | 融合归一化改变了中间舍入和求和顺序，导致后续生成分叉。先按参考顺序对齐，再修改 AITER 原生实现，保留必要的请求分组和舍入边界。 |
| 6 | 批处理 Linear | 请求合批改变矩阵形状，底层会选择不同计算算法；逐请求计算虽然稳，却慢。先保留逐请求形状，再为已验证形状选定原生 hipBLASLt 算法，恢复批量执行。 |
| 7 | Q/K/V 投影 | 将投影合在一起计算会改变矩阵形状和数值路径。预填充阶段按参考方式拆分 Q、K、V，避免从注意力输入处就产生偏差。 |
| 8 | 输出词表投影 | 为保证输出一致而逐行计算词表分数，限制了并发效率。对已覆盖形状启用验证过的原生批量投影，其他情况保留兼容路径。 |
| 9 | MoE 数值顺序 | 专家计算中的累加顺序、激活舍入和路由加权方式与参考不同。修改 CK 中对应的计算与 BF16 边界，先保证专家输出的计算方式一致。 |
| 10 | Decode 专家计算 | 参考实现需要拆开计算，部分路径还要收集、复制被选中的专家权重。恢复原生 CK 两阶段批量计算，并选择适合小批量生成的分块参数。 |
| 11 | Prefill 专家计算 | 不同专家收到的 token 数不同，统一使用一种计算参数容易失配。根据专家分组形状制定 GPU 执行计划，使用经过验证的原生前向和回投影计算。 |
| 12 | Router 计算 | 路由计算及类型转换产生额外开销，融合时又容易改变权重舍入。启用保持参考 BF16 语义的原生融合路由。 |
| 13 | 路由计划复用 | 专家计算前后两阶段重复排序、计数和准备索引。复用两阶段都能使用的路由计划，并跳过不需要的准备工作。 |
| 14 | 专家结果合并 | 多个专家原子累加到同一个输出位置，累加顺序可能变化。改为每个专家写独立槽位，再按固定方式归并，并将槽位寻址放进原生 kernel。 |
| 15 | Prefill 请求并行 | 为保留每个请求的计算形状而串行处理，请求之间无法充分并行。使用受控的 GPU stream 并行执行独立请求，同时管理依赖与缓冲区生命周期。 |
| 16 | KV 布局与历史长度 | ATOM 的分页缓存、V 的重排布局和参考实现的历史范围不同。明确缓存读法与滑窗保留长度，使注意力真正读到对应的历史 token。 |
| 17 | Decode Attention | 显式取出历史缓存，再用多个 PyTorch 算子计算，搬运与启动开销大。接入修正后的 AITER/Gluon 分页注意力，在保留计算边界的前提下恢复原生执行。 |
| 18 | 滑窗与全局因果 QK | 滑窗只计算窗口内区域；全局层跳过未来位置，并对兼容形状只派发三角区域任务。保留原MFMA与累加顺序，未知形状回退。 |
| 19 | 滑窗 PV | 概率与 V 相乘时仍遍历大量无效区域，尾块的累加方式也会影响结果。跳过窗口外计算，为尾块采用匹配的计算方式，并对读取施加有效范围掩码。 |
| 20 | Scale / Mask / Softmax | 缩放、掩码和归一化分开执行，需要多次读写大张量。将这些步骤融合，同时保留参考归约顺序、舍入和指数下溢处理。 |
| 21 | Attention 缓存与分块 | 长输入的中间张量和重复读取开销大，单一缓存策略不适合所有长度。按形状选择行缓存或窗口缓存，并采用头部分块和 QK 分片控制工作区与执行粒度。 |
| 22 | CPU 请求元数据 | 每一层重复读取请求边界和长度，产生 CPU 工作和同步。每次前向只准备一次并跨层复用，同时限定缓存生命周期，避免复用旧请求信息。 |
| 23 | 分段编译 | RoPE、激活等小计算段由 Python 逐个提交，启动开销明显。只编译稳定的张量计算段，并显式保留精度转换，避免融合悄悄改变舍入。 |
| 24 | Decode Graph | 每生成一个 token 都重复提交相似计算；图重放又要求地址和元数据稳定。启用 ATOM 的 decode graph，稳定偏移和缓存地址，减少重复提交。 |
| 25 | 启动预热 | 总 token 预算增大后，预热可能构造出超出已覆盖范围的单条长请求。限制合成预热请求的长度，保留实际服务的请求长度和调度配置。 |
| 26 | MTP 模型接入（独立分支） | 通用投机路径不能直接理解 Mellum 的草稿头。补齐草稿模型注册、独立权重映射和前向计算，并核对注意力类型与主模型隐藏状态。 |
| 27 | MTP 验证计算（独立分支） | 验证阶段每个请求包含多个位置，不能沿用普通单 token 解码的全部假设。补齐因果注意力处理，并修正 GEMM/Norm 的行分组，保持目标模型计算语义。 |
| 28 | MTP 图与元数据（独立分支） | 草稿和验证交替执行时，元数据与图缓冲区复用更复杂。修正相关生命周期与隔离，避免图重放读到已经变化的状态。 |
| 29 | MTP 的 KV 预留（独立分支） | 只给输入分配缓存，新请求可能挤占老请求继续生成的空间，触发有问题的抢占重算。接纳请求前预留生成和验证所需空间，避免在该配置下进入错误路径。 |
| 30 | MTP 草稿投影（独立分支） | 草稿头的特殊投影仍逐行执行，额外开销抵消投机收益。只将草稿生成阶段的投影批量化，保持目标验证路径不变。 |
| 31 | MTP 基线同步（独立分支） | MTP 启动入口一度指向旧代码和参数，比较时混入了版本退化。将 MTP 接到当时已冻结的快版本，使用同版关闭组重新做开关对照。 |
| 32 | 参考路径与逐层探针 | 只看最终文本，无法知道哪里第一次算错。增加固定输入、中间张量和逐 token 对照；这些工具用于定位，不作为默认高性能实现。 |
| 33 | 验证与性能脚本 | 旧服务、不同输入协议和小样本结果容易混在一起，无法判断修改是否有效。固定参考、输入、启动配置和版本，返回真实 token IDs，并分别运行正确性、完整性能和开关消融。 |
| 34 | 启动与依赖交付 | 源码正确但依赖二进制或环境开关不同，实际运行仍可能走另一条路径。提供一条命令启动、独立优化开关、依赖与源码哈希校验，并以真实生成验证启动成功。 |

以上按具体实现展开；正式报告将性能优化归为 MoE、Attention、编译与图执行三个点。MTP 在独立分支开展过开关对照，但不属于当前默认交付配置。
